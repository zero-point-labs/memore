# Memora Experience Platform Enhancement - Product Requirements Document

## Executive Summary

Memora is a student-focused trip and event organizing company in Cyprus. This project enhances the platform by adding clarity about what Memora is, introducing a new events system for single-night parties, and implementing a complete payment and notification system with Stripe integration.

---

## Problem Statement

### Current Issues
1. **Unclear Value Proposition**: Visitors don't immediately understand what Memora is or what services they offer
2. **Limited Event Types**: Only 3-day adventures are offered; no single-night events (parties, club nights, beach bars)
3. **Manual Payment Processing**: No automated payment system, split payment capability, or booking management
4. **No Notification System**: No automated email/SMS notifications for bookings and payments
5. **Poor Information Architecture**: Content flow doesn't guide users through understanding → exploration → booking

### Business Impact
- Lost conversions due to confusion about services
- Missed revenue opportunities from single-night events
- Manual administrative overhead for payments
- Poor customer experience due to lack of communication
- Difficulty scaling operations

---

## Goals & Success Metrics

### Primary Goals
1. **Increase Understanding**: 80%+ of visitors should understand what Memora offers within 30 seconds
2. **Expand Revenue Streams**: Launch events system to capture single-night party market
3. **Automate Payments**: Implement split payment system (30% deposit + 70% before trip)
4. **Improve Customer Experience**: Automated notifications at every booking stage
5. **Reduce Manual Work**: 90% reduction in payment-related administrative tasks

### Success Metrics
- **Conversion Rate**: Increase by 40% (better clarity → more bookings)
- **Average Booking Value**: Track separately for trips vs events
- **Payment Success Rate**: >98% for automated charges
- **Notification Delivery**: >95% for SMS, >98% for email
- **Customer Satisfaction**: >4.5/5 rating on booking experience
- **Administrative Time**: Reduce payment processing time by 90%

## 3. Payment System Integration

### 3.1 Split Payment Architecture

#### Payment Flow for 3-Day Trips
1. **Initial Booking (30% Deposit)**
   - Customer completes booking form
   - Selects package and preferences
   - Saves payment method with Stripe
   - Pays 30% deposit immediately
   - Payment method saved for future charge

2. **Balance Collection (70% - Automated)**
   - Scheduled charge 7 days before trip start date
   - Automatic charge to saved payment method
   - 3 retry attempts if first charge fails
   - Customer notifications at each stage

#### Payment Flow for Events (Flexible)
- **Option A**: 100% upfront (recommended for single-night events)
- **Option B**: 50% deposit, 50% 48 hours before event
- **Option C**: Same as trips (30/70) for expensive events

### 3.2 Required Stripe Components

#### Stripe Products to Implement
1. **Payment Intents**: For immediate charges (deposits)
2. **Setup Intents**: For saving payment methods
3. **Payment Methods**: Saved cards for future charges
4. **Customers**: Stripe customer objects linked to Appwrite customers
5. **Webhooks**: For payment event handling
6. **Invoices**: For payment records and receipts

### 3.3 Stripe API Endpoints

**Required API Routes:**

1. `/api/payments/create-deposit`
   - Creates Stripe customer if new
   - Creates payment intent for deposit
   - Saves payment method for future use
   - Creates booking in database
   - Schedules balance payment
   - Triggers confirmation notifications

2. `/api/payments/process-balance`
   - Retrieves scheduled balance payments
   - Charges saved payment method
   - Updates booking status
   - Triggers success/failure notifications
   - Schedules retries if failed

3. `/api/payments/update-payment-method`
   - Allows customer to update saved card
   - Creates new setup intent
   - Updates payment method in Stripe + database

4. `/api/webhooks/stripe`
   - Handles Stripe webhook events
   - Processes payment confirmations
   - Updates database statuses
   - Triggers notifications

5. `/api/payments/cancel-booking`
   - Cancels pending balance charges
   - Updates booking status
   - Processes refunds (if applicable)
   - Sends cancellation notifications

## 5. N8N Automation Integration (Optional but Recommended)

### Purpose
N8N provides visual workflow automation to reduce custom code and improve maintainability.

### N8N Workflows to Create

#### 5.1 Payment Processing Workflow
- **Trigger**: Scheduled cron (daily at 9 AM)
- **Steps**:
  1. Query Appwrite for balance payments due today
  2. For each booking:
     - Check payment schedule status
     - Retrieve Stripe customer and payment method
     - Create payment intent for balance amount
     - Process charge
     - Update booking status in Appwrite
     - Trigger notification workflow
  3. Handle failures with retry scheduling
  4. Send admin summary report

#### 5.2 Notification Workflow
- **Trigger**: Webhook from payment processing
- **Steps**:
  1. Receive booking and event type
  2. Fetch customer communication preferences
  3. Select appropriate templates
  4. Personalize content with booking data
  5. Send email via Resend
  6. Send SMS via Twilio (if opted in)
  7. Log notifications in Appwrite
  8. Track delivery status
  9. Handle failures with retries

#### 5.3 Payment Reminder Workflow
- **Trigger**: Scheduled cron (daily at 10 AM)
- **Steps**:
  1. Query bookings with balance due in 7 days
  2. For each booking:
     - Fetch customer details
     - Generate reminder content
     - Send email reminder
     - Send SMS reminder (if opted in)
     - Update reminder sent flag
  3. Send admin report of reminders sent

#### 5.4 Failed Payment Recovery Workflow
- **Trigger**: Webhook from failed payment event
- **Steps**:
  1. Receive failed payment details
  2. Increment retry counter
  3. If retries < max:
     - Schedule next retry (24 hours later)
     - Send customer notification with update payment link
  4. If retries exceeded:
     - Send final warning to customer
     - Notify admin for manual intervention
     - Mark booking as "payment-failed"

### N8N Setup Requirements
- Self-hosted or cloud instance
- Integration credentials:
  - Appwrite (endpoint, project ID, API key)
  - Stripe (secret key)
  - Resend (API key)
  - Twilio (account SID, auth token, phone number)
- Webhook endpoints exposed to internet
- Cron scheduling configured

### 7.3 Data Flow

**Booking Flow:**
```
1. User submits booking form
   ↓
2. API creates Stripe customer (if new)
   ↓
3. API creates payment intent for deposit
   ↓
4. User completes payment with Stripe Elements
   ↓
5. Stripe webhook confirms payment
   ↓
6. API creates booking in Appwrite
   ↓
7. API schedules balance payment
   ↓
8. API triggers notifications (email + SMS)
   ↓
9. N8N workflow sends notifications
   ↓
10. User receives confirmation
```

**Balance Payment Flow:**
```
1. N8N cron job runs daily (9 AM)
   ↓
2. Queries bookings with balance due today
   ↓
3. For each booking:
   ↓
4. Retrieve saved payment method from Stripe
   ↓
5. Create and confirm payment intent
   ↓
6. Update booking status in Appwrite
   ↓
7. Trigger notification workflow
   ↓
8. Send success/failure email + SMS
   ↓
9. If failed: Schedule retry + send recovery email
   ↓
10. Admin dashboard updated with results
```

## 12. Risks & Mitigation

### Technical Risks
1. **Stripe payment failures**
   - Mitigation: Retry logic, customer notifications, admin alerts
   
2. **Automated charge timing issues**
   - Mitigation: Buffer days, manual override capability, monitoring

3. **Email/SMS delivery failures**
   - Mitigation: Multiple provider options, retry logic, fallback methods

4. **Database scaling issues**
   - Mitigation: Proper indexing, query optimization, caching

### Business Risks
1. **Customer disputes over automated charges**
   - Mitigation: Clear terms, advance reminders, easy contact support

2. **Payment processing costs**
   - Mitigation: Monitor transaction fees, optimize payment flow, bulk operations

3. **Regulatory compliance**
   - Mitigation: Legal review, proper disclosures, data protection measures
